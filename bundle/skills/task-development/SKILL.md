# 方案约束开发

先按 Host 绑定的 spec.kind 选择对应工具，不按文件名猜测契约。新任务不套用 s35 样例。
审批正文若承诺仅记账或不写文件，不能通过开启运行能力把旧方案转为执行许可；须重新形成真实执行方案并获可信审批。

## workspace-v1 多文件开发

- 入口通过 task_approval_request 提交精确方案，只登记不执行；独立审批有效且运营方匹配绑定后，
  task_development_start 立即返回排队回执，由云端独立 worker 执行，不占用入口会话。
- 使用 development_workspace_read 查看批准文件、只读输入、命令、预算和整个工作区的 base_version。
  指定 path 才读某个批准文件；返回的文件 SHA 不能冒充整个清单的 CAS。
- development_workspace_write 每次只修改一个批准路径。新增/修改用 action=write 和完整 content；
  删除用 action=delete 且省略 content，不传 null。base_version 原样复制；写入后返回新的清单版本。
- development_workspace_command 只传批准 command_id，不传 argv/env/shell 覆盖。输出是临时构建日志，
  不是自动回写或已登记成果。源码改变后重跑全部 required 命令，失败按预算修正，不擅自改变验收标准。
- 所有必需命令与当前清单匹配后 development_report；插件登记实际文件、命令及模型派发证据。
- 模型策略来自任务和批准方案；每次流派发前持久预留预算，失败/未知也不返还。
  succeeded 仅表示模型流正常结束，不是开发完成或供应商计费凭据。
- 需要 development_workspace:1 和 job 0.22.0；缺能力/禁用即停止，不降级旧 worker 或原生工具。

## bounded-js-v1 历史样例

1. 确认当前 Host 提供 development_read、development_write、development_test 和 development_report。
   缺能力就停止，不能用 shell、第三方插件或旧 RepositoryWriter 替代。
2. development_read 只读已绑定的新文件。将返回的 base_version 字符串原样用于 development_write.base_version。
   不存在时返回 "absent"；存在时返回 "sha256:" 加 64 位哈希。不要传 null、"null" 或旧 expected_hash 字段。
   例如读取结果为 {"base_version":"absent","content":null}，写入参数是
   {"base_version":"absent","content":"本次批准的完整源码"}。
   不自行构造路径、任务 ID、epoch、审批 ID 或版本标记；标记不是授权，插件仍核验真实文件和权限。
3. 实现本次指定的 summarize 函数，development_write 只写一个已批准文件，不能提交或推送。
   该有界样本与最多三次写入仅属于本次验收，不是以后每项任务的默认要求。
   本次测试器只支持纯函数子集：导出 `function summarize`、const、if、return、throw、普通对象、
   算术逻辑、Number 的整数／有限数检查、Math.round/floor/ceil，以及本地数组的 some/every。
   不使用 import、循环、递归、赋值、动态属性、其他全局对象或包；这不是通用 JS 沙箱。
4. development_test 使用插件自带六项测试，无任意命令参数。失败后可在批准预算内修正，再测试。
5. 测试通过再 development_report；摘要不能宣称远端已交付。插件从文件 hash 与测试记录自动登记报告。
6. 工具显示已保存但批次仍运行时，不声称已安全交接；Host 排空和持久提交决定成果是否可打开。
7. 若取消、审批过期/撤销、模型或内容版本不匹配、重启待核对，停止；不能换 ID、提权或重试来绕过。
   参数被拒也必须如实报告调用次数，不能把“零次落盘”解释为无限重试；运营方核对后才能继续。
8. 运营方确认零效果并受控恢复时，保留原任务、审批、失败批次和尝试次数；先恢复为暂停状态，
   再由运营方显式恢复已批准的一轮。该恢复能力不是模型工具，不能自行调用或伪造恢复证明。

## 排空与版本诊断

- 取消、错误回调或主会话空闲不能作为写入权交接依据；以自有插件的进程关闭与持久操作记录为准。
- 有未关闭测试操作时，即便未写文件，也不能用“零写入恢复”直接清除围栏。保留记录，交由运营方核对，不能按 PID 猜测并杀进程。
- 调度器提示 SCHEDULER_OWNER_CHANGED 时停止启动，核对既有 Host/锁端口；不改端口、目录或编号强行启动第二个消费者。
- 旧 bounded-js-v1 执行要求 development:2 与 job 0.21.0；workspace-v1 使用上文 0.22.0 契约。旧任务保留原版本与失败证据，不重登记来绕过审查或追加预算。
- 旧单文件测试器仅支持已批准的固定纯函数验收，无派生进程能力；它不能代替新版容器构建边界。
- 排队请求同时固定实际工作区和 Git 目录身份。路径同名、HEAD 相同也不允许替换检出；身份变化时停止核对，不重新入队绕过。

## 旧契约双端共享写入通道

- development_bridge:1 是自有插件内部通道，默认关闭，不是普通聊天可调用的新原生工具。
- 方案必须明确 executors；旧云端审批不能自动授权本地。票据只约束已批准的云端受管检出，不是本地文件系统权限。
- 本地提交候选内容，云端同一写入门禁负责落盘和固定测试；不得用本地 git/shell 绕过，也不自动提交、推送或发布。
- 本地持久入队、云端排队、取得写入权、测试结束、交接完成分开报告；取得票据本身不会启动模型。
- 断线或重启后结果未知保留原请求与围栏，不重新领取票据、不自动重放写入。已排队但未持权的请求才可直接取消。
- “managed_cloud_io_only”只说明受管云端文件/测试通道已关闭，不证明本地任意 Agent、Shell 或原生工具均已排空。

## 未知回执核对

- development_review:1 只供运营方显式核对。读取证据不会重发写入、解除围栏或启动模型。
- 原请求、调用指纹、审批、文件哈希、工作区身份和实际进程关闭证据全部匹配，才能认领已完成回执。
  仅有意图、文件存在或相同内容不足以认定成功；缺证据、历史指纹缺失或未关闭操作继续待核对。
- 继续执行需运营方用当前证据显式恢复：保留原请求与已消耗预算，递增 epoch 并更换绑定本进程的票据，旧票据失效。
  过期或撤销的审批不能因此恢复；这不是重新批准或新增写入次数。
- 恢复回执未知时只核对原事件，不能换事件重做。重启后取回的旧进程票据不允许执行，须再次核对并显式换绑。
- 已完成交接但回执丢失只补齐完成记录，不重新开放写入。证据陈旧时重新查询，不能跳过检查。


## 首次取权回执与旧调度库

- `development_claim:1` 在取权发送前持久保存恢复凭据；初次取权回执丢失后，只核对原请求的回执。
  找回票据不授予执行，仍需原审批、同一工作区、实际排空及显式复核轮换；不重置预算。
- 原发送凭据缺失、旧端不支持、未发现已提交取权回执、审批失效时保留待核对，不换编号重试或猜测未取权。若明确取消，可请求取消原排队项；云端须确认它仍未取得持权，已持权则拒绝取消。
- 恢复凭据、票据与端点密钥不进入模型输出、聊天或 UI。该核对属于插件内部操作，不是普通模型工具。
- 已存在但没有 scheduler_owner 的旧任务库须离线迁移。迁移用实际旧配置的锁端口，先确认旧 Host 停止并备份；
  不猜一个空闲端口，不删除库或清空预算来启动。迁移只绑定 owner，不恢复或批准执行。


## 多文件方案候选边界

`workspace-v1` 的新版原生 worker 仅在运营方明确启用 workspace.enabled 的云端 Host 可用；
新版双端写入要求 development_workspace_bridge:1。遇到 WORKSPACE_DISABLED / CONTRACT_METHOD_MISMATCH 应报告缺能力或契约不匹配，
不能降级到单文件样例、调用 shell 或把方案改成旧格式绕过。

- 文件的新增、修改、删除及只读输入分别绑定相对路径和批准基线；按当前任务实际需要设计，不固定为 s35。
- 构建命令绑定已安装镜像的完整 SHA-256、argv、cwd、超时和次数；不能只批准模糊的“构建一下”。
- 命令在源快照只读、无网络的独立容器中运行；临时输出不自动回写仓库或成为已登记成果。
- 每次源码变化使此前构建证据失效；全部必需命令须匹配当前文件清单摘要，模型口述通过不能替代。
- 取消/超时只触发停止请求，须容器实际停止证据才能记排空；未知容器状态保留请求和占用。
- 模型仍由任务策略决定；容器不是新的模型选择或全局身份隔离，也不授予提交、推送、发布权限。


## workspace-v1 双端受管通道

- development_workspace_bridge:1 使用独立 workspace_bridge 方法族；旧桥不能处理新方案，不能降级后重发。
- 本地只提交批准路径的候选内容及 command_id，云端同一 Gate 负责 CAS、预算、容器和排空。
  不是本地文件系统租约，不自动启动本地模型，也不替代原生 DSH 工具权限。
- 多文件写入指纹包含路径；命令指纹包含精确 command_id 和当次清单摘要。
  回执丢失只能认领原调用的持久完成证据，不重跑命令或给失败请求换编号。
- 同时核验命令完成记录及对应实际关闭操作；仅有容器名字、退出码、文件存在或客户端结束不够。
  容器排空未知或命令结果未记账时仍保留围栏，不能用单文件恢复器假装已核对。
- 已完成回执可以补齐，但继续操作还要显式复核原请求并轮换 epoch；预算和原失败记录不清空。
- 命令 RPC 等待上限覆盖批准命令的最长 300 秒及传输余量；连接超时不等于容器已停止，不能据此交接。


## 中断容器的运营方核对

仅运营方可在原调度锁独占、当前任务无活跃执行时，核对原命令意图、完整容器 ID、镜像与工作区。
必要时显式停止该容器；进程退出、名字相同、容器不存在、dead 或尚未启动都不算排空证据。
核对只补“已排空但结果不可信”的失败回执，不补测试通过、不解锁、不启动 worker、不返还预算。
停止回执丢失时核对同一持久事件；不能换编号重做。过期审批可以排空清理，不能恢复执行。
继续操作仍须原审批有效及单独显式恢复；模型不能调用此内部核对，也不能用旧单文件恢复器替代。


## 原生多文件 worker 中断恢复

原生开发批次中断后不自动重跑。运营方核对原审批、物理工作区、已应用文件、命令排空及模型预留后，
可为原 job 追加一轮调度尝试，但先恢复为暂停；写入、命令、模型预算均不增加。未知模型派发仍计消耗。
须另行显式恢复，重新领取围栏和新会话。worker 先读现有文件与历史命令，保留符合要求的已有内容，
不得为重建上下文而重复写入。未完成操作、过期审批、耗尽预算继续待核对，不用旧零写入恢复器绕过。


## 入口与后台任务的独立性

入口排队回执与后台完成分开表达。后台开发期间，原生聊天保留独立会话与原生工具；聊天成功不代表开发完成、任务空闲或写入权已交接。验收“入口仍可聊天”必须有后台运行期间的真实模型回复，不能只凭 idle 或工具列表。


## 有界修复与求助

验收命令失败后，先读实际失败输出，按批准方案与剩余预算修复，再运行当前清单的全部必需命令。
不能修改验收标准、删失败记录或用换请求/任务来重新计预算；三次不是全局固定次数。
预算不足或失败原因无法排除时，停止调用，解释问题及所需决定，不宣称完成。
插件保存失败快照和求助检查点；needs_review 是停止待核对，不代表已安全交接或自动获准恢复。
失败快照不是成功成果，历史快照不能覆盖当前状态。恢复仍核对原审批、文件、实际排空与剩余额度。

受管 workspace 开发与交付分支支持 dsh-task/ 和 acceptance/ 两个命名空间；这不授予执行权。只能使用用户指定、当前方案绑定的精确分支；禁止擅自换分支或写 main。开发、提交、推送分别审批，验收分支也不豁免。
