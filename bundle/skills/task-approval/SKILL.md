# 任务方案与聊天确认

### 审批引用与入口旁路回复

- 用户回复既有方案／回执／操作提示时先加载 task-approval；有完整引用则用 task_approval_reference 查原文。
  仅传实际引用全文，不拼造缺失内容，不先按名字猜任务或选择最新方案。
- quote_is_authority=false：引用、标题和语义本身不是批准。current_reply_verified=false：即使查到 approved，
  也只说明该时刻的账本状态，不证明当前这条回复已被核验，不代表执行开始或完成。
- match=unresolved/ambiguous/state_unavailable，或能力缺失／离线时，仅说“本入口尚不能核验这条回复”，
  优先用返回的 suggested_reply 一句话回答，不额外追问；不能说“任务不存在／审批失败／需要重新批准”。
  可能是其他实例、截断引用或历史格式，不替用户猜原因，也不展开解释这些可能性。
- 用户仅告知“我已回复／已确认”而未明确要求查账时，没有完整引用就不调用查询、不构造原文、不查目录。
  只答“本入口尚未核验这条回复；请以原方案的审批账本回执为准，无需重复批准。”
  不调用 ask_user_question，不弹窗，不追问任务名、编号或是否要查询，不展开审批教程。
  用户明确要排查状态时才继续按名称查询，查询不生成新申请、不重新批准、不恢复任务。
- 结果通知／提示不是待审批方案。若要改变决定，引导定位原方案；不要回复结果通知来改变权限。
- 原生入口至多作一次简短、非权威的状态说明，不冒充账本回执，不把回执 queued/needs_review 当审批失败。
  不吞消息、不接管 IM 消费者、不注册 /yes 全局命令，不改原生 slash command、工作模式或工具权限。


1. 用 task_catalog 按名称定位；同名先澄清。读取 task_status 的当前修订、用户原文和模型策略。
2. 方案说明概述、变更、验收、风险、回滚和确切 model_policy。不猜 provider，不改变入口模型。
3. 用户要求送审后调用 task_approval_request。scopes 仅列明确请求的动作；develop、commit、push、publish、deploy 互不包含。未关联时 repository 为 null；已关联则先加载 task-repository 并刷新，repository 只传 binding_revision 与 fingerprint，不把链接当权限。服务端将仓库身份、分支、基线写入不可变方案。
4. 根据返回的 chat_confirmation 说明状态：queued 是待发送，sent 是平台已接收，不表示已读。needs_review 必须核对，不重复申请绕过未知发送结果。
   用户在已配置机器人私聊中“回复具体方案消息”，根据 instruction 自然语言表达意见（如“确认”“不批准”“先等等”或修改意见，也可 /yes）；不要求记忆任务编号。没有回复关联的裸发不会批准。
   绑定云端机器人时明确引导用户去云端私聊，本地入口可以送审，但不能假称本地确认已获验证。
5. 插件独立回查官方平台原始消息，核验用户身份、消息时间、回复关系、方案未修改及当前修订后记账。模型只查询 task_approval_status，不调用直接批准接口，也不能用聊天摘要替代证据。
   收到方案回复时不重复创建申请；按已知任务查询一次账本即可，未有决定只能说明“已收到，待核验”，不得假称已记账，也不占用主会话循环等待。
6. 拒绝、暂缓和修改意见同样写入账本。changes_requested 冻结旧方案，须保全 feedback.user_text 并重新送审；不能把“可以，但是……”拆成批准旧方案加后续修改。held/clarification_required/confirmation_review 均禁止执行。过期、修订变化、替换方案、撤销或批准人绑定失效均禁止沿用旧授权。
7. confirmation_url 目前返回空，不再提供旧注册网页。新路线以本地工作台的具体任务为主、本地 IM 绑定对话为辅；复用已有可信身份，不要求通行密钥或新账户。已显式配置 localApproval 的双端通过本地 IM 核验窗口后逐案保存；旧 cloud 绑定只在未迁移实例保留，不凭版本猜测实际入口。

## 边界

- 当前首个适配器只支持明确绑定的飞书私聊；其他平台、群聊、裸发确认均不能声称已支持。
- 原生聊天、斜杠命令和工具权限继续由第三方 IM 处理；不接管消费者、不改源码、不读其私有文件作为信任依据。确定与 /yes 不注册为全局拦截命令。
- 平台账号是身份边界，不证明操作设备或当前操作者的生物特征。共享管理员/根账号可改库风险不由本协议解决。
- 测试自动化发送的确认只用于隔离夹具，不能记成用户授权生产任务。批准人注册、业务批准不可代办。
- 无方案引用的裸发“同意”、对端消息、node token、原生工具批准、历史文本、编辑/撤回消息都不能代替当前可信回复。
- 受管执行器默认关闭，实际开关须查运行时，不能用版本名称推断所有执行器状态。approved 是授权记录，
  不是执行能力已开放或工作已完成；不能调用旧 runner、bash、git push 绕过。
- 普通短问答保留原模式、原模型和原生工具，不强制转后台。

### 账本权威回执

- 审批决定与回执意图由插件在同一事务保存；模型不生成、补发或冒称“DSH 审批账本回执”。
- 查询 task_approval_status，分别说明账本的有效 state 与 chat_confirmation.receipts 的投递状态。
  已批准但回执 queued/verifying/needs_review 不能说尚未批准，也不能重复申请或替用户再批一次。
- 回执 sent 只表示官方 API 回查到匹配消息，不表示用户已读。发送结果不明时待核对，不让用户重复确认来绕过。
- 回执注明生成时刻与方案版本，仅是当时快照。后续过期、修订、撤销或身份失效，以当前账本查询为准。
- 普通模型回复不等于权威回执；受管开发默认关闭；仅明确启用、精确绑定当前任务并通过门禁的受管 worker 可执行，发布仍关闭。账本批准不等于任务开始或完成。

## 语义与故障处理

- 按返回的 instruction 使用对应协议；升级不重解旧方案里以前未识别的消息。
- 自然语言批准只针对原方案；条件、额外范围、预算、模型、文件和仓库变化都形成修改意见，不能执行旧方案。
- 语义解释调用独立的有界无工具模型，不占用入口会话；无法判断或调用失败时回执“待澄清”，不自动重试成批准。
- 身份来源由插件核验，解释器只理解直接决定。代理输入等审计说明不自证授权，也不等于修改意见；
  不隐藏原文或声称本人手打。规则升级不得重解旧待澄清记录；核对后仍须新的有效回复，不能用短口令绕过。
- 暂缓可在同一未过期方案下重新明确批准；修改意见必须形成新方案后再次确认。模型不能替用户点选、重写或补造批准。
- 其他 IM 的报错与审批记录独立。先查询当前账本有效状态及投递状态；不得把 INTERNAL_UNKNOWN 解释为批准失败而要求重批。
- 运行开关关闭或任务被明确暂停时，历史 approved 不能恢复执行；指定回归和本人验收完成前，不启动开发 worker 或应用写入绑定。

### 方案与结果通知的区分

- 【DSH 方案确认】标为“待你决定／请回复本条”，这是审批入口；【DSH 审批账本回执】标为“结果通知／无需回复”，不是新方案。不要把相同任务名当成相同消息。
- 回执引用原方案时，先点击引用定位原文，再对原方案使用“回复”。如果回执没有引用，按任务名称找到原方案；不要求输入编号或固定口令。
- 误回回执不改变审批。自有插件只核验本人及已保存回执，给出一次持久化操作提示；不调用语义模型、不重新批准、不追溯解释升级前的误回复。模型不得冒充该提示或建议反复重发来绕过 IM 报错。
- 原生 IM 兼容性与审批账本独立；修复应优先使用已回归的上游发布包，不给第三方打补丁、不替其注入隐式 owner 身份，不改变原生工具权限。运行开关关闭或任务暂停时，修复 IM 不恢复开发。

新送审方案未指定思考程度时，协调器将 `high` 写入方案后再计算审批摘要；显式值优先。不得在批准后改变策略或重写历史审批。已有方案因网络重放应返回原账本，不套用当前默认值。辅助模型阶段仍需独立明确策略。


## 绑定交付预览

提交送审应先加载 task-repository，使用真实预览的 opaque 引用及明确提交说明，proposal.delivery 由云端展开。
提交方案只支持 [commit] 的精确授权，不接受混合 develop/push/publish/deploy。批准本身不启动执行器；实际提交另须当前运行开关、精确计划与交付门禁。
审批正文/回执显示绑定分支、基线、测试内容、文件集合和提交说明；用户按任务名在工作台逐页查看全文，不必输入编号。
查询与确认不自动重验文件，因此“已批准”指向不可变内容，不是当前工作区锁。缺失/变化的预览为 delivery_changed，不放行。
自然语言修改意见、暂缓、拒绝和撤销仍走原可信语义审批；不得代替本人批准真实业务交付。


### 独立推送审批

推送必须引用 task_delivery_push_prepare 返回的不可变计划，scopes 仅为 push，不与 commit 混用。
方案和账本回执明确使用“限定推送授权”，说明准备时远端旧值、已完成本地提交、目标仓库与分支、最多一次。
自然语言修改分支、条件同意或暂缓不执行旧方案；重新准备并送审，不让模型自行替换已批准旧值。
网页与聊天入口共用相同账本。已批准仅证明许可，是否排队／发送／远端接受查询交付动作，不由回执推断。

### 真实执行方案与仅记账方案

- 新方案区分“只验收记账”和“批准后可受控执行”。按用户本次意图与当前运行时查询说明，不因暂未开启能力就把真实开发永久写成仅记账。
- 真实执行方案写明：批准后仍须运营方精确绑定、当前能力、仓库基线与门禁，并经独立调度才执行；开发不包含 commit 或 push，发布和部署仍关闭。
- 旧方案正文若承诺“批准仅记账／不会写文件”，不能在其后打开开关直接执行；先修订并重新送审，不修改旧方案或追溯扩大授权。
- 普通业务批准仍由用户完成。仅用户明确授权的限定验收允许自动化代输入，须标明代理输入、绑定指定任务与动作，不冒称本人手打，不扩用到其他任务或真实业务。


## 第03步工作台内决定

- `approval_interaction:1` 是独立交互协议。旧 `approval_workbench:2` 只读查询身份接线状态，不产生决定；退役注册接口保持拒绝，不降级。
- 用户在具体任务输入意见或点同意／暂缓／拒绝，先看解释与完整方案，再点“保存这次决定”。完整输入优先；有条件同意保存为修改重审，旧方案禁止执行。
- 首次通过已绑定审批私聊核验这个窗口：对照窗口校验并回复专用身份消息，明确允许10分钟内逐项决定。身份消息不是方案、不是任务批准，不要求新账号、通行密钥或固定 DSH session。
- 显式启用 localApproval 后，身份确认、方案和回执统一本地已绑定私聊；绑定包括机器人、私聊与批准人，App ID 或收到通知不够。旧 chatApproval 不自动改绑，二者不能同时配置。
- 每次保存重查平台原消息、本人回复和当前绑定，并核对方案摘要、任务修订、原决定及有效期。刷新或关闭页面丢弃窗口能力；绑定变化、后续矛盾回复或证据不可读不放行。
- 浏览器能力不入模型上下文，不提供模型工具代发身份请求或保存决定。已核验窗口不自动批准其他任务；结束窗口身份不撤销已记账的独立方案决定。
- 处理未知先查询原操作。只有明确未收到“意见核对”且从未发送“保存决定”，才可由用户返回修改后重新核对；保存未知不得换编号重试。重启不重解在途意见，不重发确认，不执行旧任务。
- 本步骤不启动 worker、不解锁仓库，不把暂缓决定称为暂停在途任务；工作台回执来自账本。IM 回执沿用本地方案投递记录；未送方案不猜收件人。本地离线等待，不回退云端机器人，不把等待称为已发送。

## 第04步本地 IM 辅助入口

- 自有配对协议仅转交有界的平台查询和固定私聊发送；云端独立核验原提示、本人回复、引用与原文，再写原审批账本。IM 内部 session 改变不改变任务归属。
- 本地 IM 凭据仅保留在本地。配对令牌不是批准人；消息发送成功不是批准或已读。
- 新增同机器人同私聊的通知目标，不改已有任务默认值或订阅；业务结果仍须 task-notify 的明确目标与授权。
- 未知发送查原事务，不另发一次。断线等待不消耗未发送回执的重试预算；重启中断留核对，不重放旧消息、重新解释或启动 worker。

## 审批与异常处理分界

工作台方案审批与异常建议分开。自然语言意见不能当作清锁、重放或追加开发预算授权。异常流程见 task-sidebar；新的一批只读报告必须展示完整意见、材料范围、原模型与新限额后另行确认。不修改旧审批，不将「结束批次／通知跟进」表述为任务成功。

## 原生 Desktop 与路由迁移

- 原生 Desktop 与网页使用同一审批账本；容器身份只证明已登录访问，不代替既有 IM 的窗口核验和逐案确认。不得通过补造 Origin 或自称已验证来绕过。
- 本地平台凭据仅由本端官方 credentials.resolve 读取明确引用，不传云端、不写入提示词；撤销或轮换后重新核验，不沿用缓存令牌绕过。
- 切换审批机器人不迁移旧消息为新批准。旧有效方案、未知发送、历史任务必须先核对；切换后有新决定时禁止覆盖整库回滚。
