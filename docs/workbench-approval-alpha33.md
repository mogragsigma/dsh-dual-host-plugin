## 交互与权限

1. 在任务详情输入自然语言，或选择同意、暂缓、拒绝。输入内容优先，不能用同意按钮抹掉条件。
2. 点击“核对我的意见”，展示系统解释、原文和完整绑定方案，包括范围、模型、仓库和限额。
   此时只有持久的待验证意图，没有新批准。
3. 点击“验证身份并保存决定”，浏览器发起 WebAuthn，核验已登记审批人的签名与用户验证标志。
4. 云端在同一事务中复核方案／任务版本、当前状态及前一决定，写入证明、决定与既有回执队列。
5. 页面只根据账本显示结果。中断或结果未知时，手动查询原操作，不重复提交签名或重新解释。

| 自然语言示例 | 记账状态 | 后果 |
| --- | --- | --- |
| 就按这个方案执行 | approved | 仅批准当前绑定范围；仍须独立执行门禁 |
| 不同意这个方案 | rejected | 不执行此方案 |
| 先放一放 | held | 暂缓决定；不是声称已暂停在途 worker |
| 可以，不过请把报告改成两段 | changes_requested | 保存原文与修改意见，旧方案不可执行，须另行修订重审 |
| 这样做可以吗？ | clarification_required | 不视为批准，允许继续澄清 |

复用 `approval-semantics.js`，明确完整语句可走规则；其他表达可调用显式配置的语义模型。
模型只解释意见，不认证身份、不更换任务模型、不授予权限。未配置或解释失败时保守澄清，不猜测批准。
本轮没有为生产选择模型或配置凭据；隔离分类器测试不冒称真实模型调用。

| Before | After | Why |
| --- | --- | --- |
| 预览按钮只改变合成状态 | 意见准备与身份验证分为两步，回显真实账本 | 不把页面成功提示当成授权 |
| 批准按钮容易掩盖输入条件 | 输入原文保留，确认前明确展示解释 | 有条件同意不放行旧方案 |
| 操作超时容易重复点击 | 保留原操作引用，提供查询结果按钮 | 防止未知发送被自动重放 |
| 审批详情分散 | 当前动作内展开完整方案与修改意见 | 不再新增一排诊断框体 |

## 模块与持久化

- `ui-source/approval-workbench-client.mjs`：准备、确认、取消及原操作查询；不注册身份，不含定时器。
- `ui-source/task-focus-view.js`：输入、解释核对、完整方案、显式身份验证、结果与草稿反馈。
- `bundle/workbench-host.js`：复用官方认证的 `task-workbench/control`，只转发五项专用操作。
- `bundle/link-contract.js`：新增 `approval_workbench:1` 能力；旧对端无此能力时拒绝，不回退到聊天伪批准。
- `bundle/index.js`：本地通过现有配对链路转发，云端调用唯一账本，不新增原生模型审批工具。
- `bundle/approval-workbench.js`：意图及证明持久化、事件去重、版本复核、语义准备与身份签名绑定。
- `bundle/approval-auth.js`：复用注册／验证机制，新增绑定工作台意图的挑战；不限制认证器附件类型。
- `bundle/approval-ledger.js`：验证工作台证明、记录语义决定并复用权威回执；不伪造聊天来源证明。
- `bundle/task-board.js`：只读投影已记账修改意见；不改变任务状态或调度。
- `scripts/prepare-enrollment.mjs`：管理员离线生成一次性邀请，私有独占文件输出，不公开为模型／RPC 工具。

新增两张自有表：`approval_workbench_intents`、`approval_workbench_proofs`。
挑战仍使用 `approval_challenges`，决定仍使用 `approval_decisions`，权威回执仍使用 `approval_receipts`。
意图绑定任务、方案、版本、前一决定、用户原文、解释和允许的浏览器 origin。
处理中断变为待核对；没有启动时自动重做模型解释的逻辑。
精确签名重放只返回原操作回执，其他重放／并发变更被拒绝。

本轮不新增 scheduler、worker、恢复、结束、提交、推送或发布调用。
批准可能满足原有执行链路的一个前置条件，但本接口不会自行发起执行。
同意不等于已经执行；暂缓／拒绝不冒称已终止其他在途工作。

## 入口配置与兼容边界

功能默认不启用。云端自有配置中显式提供 `approval.workbench.enabled` 与 origin 白名单。
示意配置如下，仅为结构说明，不是应直接写入用户配置的端口或域名：

```json
{
  "approval": {
    "origin": "https://approval.example.invalid",
    "rpID": "approval.example.invalid",
    "workbench": {
      "enabled": true,
      "origins": ["https://approval.example.invalid:8443"]
    }
  }
}
```

- 沿用已有审批身份；新环境先由管理员生成一次性邀请，由用户完成登记，不从 Host 登录自动认领身份。
- 可选 `approval.semantic` 使用既有语义模型配置结构；没有自动借用日常模型 Key 或强制绑定任务模型。
- 当前实现要求验证 origin 的主机名等于 RP ID；使用 HTTPS，或开发验收用 `http://localhost`。
  列入白名单不代替浏览器 RP 验证，不能随意跨域共享通行密钥。
- 采用标准 WebAuthn，不调用 Mac 私有接口，不强制 Touch ID，可使用浏览器支持的设备验证或安全密钥。
  这不等于已经实测 Windows、Linux、Android、iOS 或所有桌面容器。
- 不支持 WebAuthn 的容器、未获准 origin、未登记身份均拒绝准备；提示使用已配置的安全浏览器工作台。
  原生 Desktop 的非标准 origin 不会被静默信任，仍需单独验收；没有修改 DSH 容器。
- 现有 IM 审批路径与通知路由保持。所选机器人通知／审批统一、主对话入口及受控下载仍属后续工作包。
- 工作台操作引用和草稿目前仅在页面内存中保留；Host 重启不丢后台账本，但完整页面重载后的待决引用找回
  尚非已验收能力。重载后先看当前审批账本，不将旧截图当作授权。

## 隔离验收

隔离 Host 为本机两份全新官方 DSH `0.2.1-rc.3`，分别承担 local/cloud 角色。
不使用生产配置、凭据、机器人或历史任务；没有访问真实 ECS 或 Gitee。
四个原生模式 standard、ptc、cordis、minimal 均按公开 API 加载，模型调用为零。
保留各自测试 AGENTS.md 的用户规则哨兵，不将候选模板写入日常全局规则。

自动化覆盖语义四类、条件优先、未知澄清、错误 origin／RP／挑战／签名、UV、用户在场标志、身份停用、
方案替换、审批并发变化、失效、重复事件、挑战重放、重启回执、双端 HTTP 与原生工作台路由。
新增真实签名使用隔离软件认证器，不是用户本人验收或硬件安全认证器验收。

浏览器原生通行密钥自动化曾返回拒绝／超时，未通过，不绕过该错误冒称本人批准。
相关端到端界面证据按“软件签名夹具”和“浏览器真实身份验证”分别记录。
定向自动化回归共 376 项：375 通过、0 失败、1 项历史比较跳过；不是完整历史回归。
旧测试中的原生工具数更新为已有的 54 项，并补全其 React 装载替身；没有新增模型审批工具。

真实官方 Host 的浏览器工作台已完成意见准备及账本回显：本地入口验证修改／暂缓／拒绝，
云端入口验证批准。签名阶段由独立软件认证器通过测试 API 完成，没有冒称浏览器系统验证成功。
四项真实测试决定分别为 approved、changes_requested、held、rejected，写入意图为零。
重启两份隔离 Host 后，六张审批相关表摘要完全一致，用户规则哨兵保留，完整性检查通过。

桌面与 390 像素宽度的布局经目视核验。原生侧栏收起动画期间会暂时挤压内容；等待布局稳定后
按钮均在可用宽度内且不重叠，手机真机不在本轮证据范围内。未完成原生系统身份验证这一项，
因此不能宣布第 02 步全部验收通过或自动进入正式部署。

## 后续与回滚

第 02 步仍需完成受支持浏览器的用户真实通行密钥验证，以及原生 Desktop 承载适配核对，才可认定全入口通过。
第 03 步的异常核对、建议修订、继续／结束不在本轮接入，不能把预览动作接到旧任务上。

候选不写入生产。本次仅在隔离目录落盘，关闭本轮确切进程即可停止服务，不按进程名误停其他 Host。
未来正式切换仍需单独批准、空闲检查和备份。回退时停用新入口，保留新增审批表和原有决定，
不得删表、恢复旧批准或重放消息来伪造回滚。已记录的修改意见／拒绝／暂缓在旧语义账本中仍保留。
